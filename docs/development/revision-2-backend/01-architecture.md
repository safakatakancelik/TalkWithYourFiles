# 01 Architecture

Part of the revision 2 backend plan. Written 2026-11-15. The other documents in this folder are `02-data-model.md` to `10-demo-scenario.md`. Reasons for every choice are in `09-decisions.md`.

## 1. What is built

A Python backend named `twyf` that stores files, agents, notes, sessions and a context map per workspace, answers questions by running a huddle of agents, and verifies every claim before it reaches the user. It has two doors: an HTTP API and an MCP server.

## 2. Components

```
 browser UI ──HTTP/SSE──┐
 any API client ────────┤
                        ▼
 MCP client ─► twyf mcp ─HTTP─► twyf serve (one process, owns the database)
 (Claude Code,  (thin client)     ├─ http/        FastAPI routes, generated from the operation registry
  Codex, ...)                     ├─ services/    one function per operation. The only place rules live
                                  ├─ orchestration/ state machine + engine that runs a question
                                  ├─ runtime/     the boundary to a model: fake | queue | command
                                  ├─ retrieval/, citations/, files/, contextmap/, agents/
                                  ├─ recording/   writes app_events for every action
                                  └─ db/          SQLite, repositories, migrations
```

| Component | Responsibility | Must not |
|---|---|---|
| `contract/` | Pydantic models for every wire type, every agent event and the operation registry. The single source of truth for types | Import anything else from `twyf` |
| `services/` | One function per operation. Validates, changes state through repositories, records events | Know about HTTP or MCP |
| `http/` | Turns each registry operation into a route. Streams agent events as server-sent events | Contain rules |
| `mcp/` | A separate process. Turns each registry operation into an MCP tool that calls the HTTP API | Open the database |
| `orchestration/` | `machine.py` is a pure state machine. `engine.py` executes its commands | Call a model directly. It goes through `runtime/` |
| `runtime/` | `AgentRuntime` protocol and its adapters | Know about huddles |
| `db/` | Connections, migrations, one repository per table group | Be called from `http/` or `mcp/` |
| `recording/` | `Recorder.record(...)` appends to `app_events` | Be skipped. Every service function calls it |

### The two doors and why they cannot diverge

`contract/operations.py` holds a list of `Operation` objects (name, HTTP method and path, input model, output model, service function). The HTTP routes and the MCP tools are both generated by looping over that list. Nobody writes a route or a tool by hand. A test fails if the three sets (registry, routes, tools) differ. See `06-mcp.md` section 2.

The MCP server is a client of the HTTP API, not a second owner of the database. One process owns SQLite, the running questions and cancellation. This is the owner's design and it is a common pattern for MCP servers that wrap an existing API.

### Who thinks

The backend never calls a model provider itself. Each piece of agent work is a **turn**: a prompt, a JSON input and a JSON schema for the output. A turn goes through the `AgentRuntime` boundary (`04-agents.md` section 6):

| Runtime | How the turn is answered | First version |
|---|---|---|
| `fake` | A script in the test | Yes |
| `queue` | The turn waits in the database. Any harness connected through MCP (Claude Code, Codex, opencode, ...) claims it, thinks, and submits the output | Yes, the default |
| `command` | The backend runs a headless CLI (for example `claude -p`) as a subprocess | Yes, small |
| `api` | A direct model API call | Designed, not built |

## 3. Technology choices

| Area | Choice | Reason in one line |
|---|---|---|
| Language | Python 3.13 or newer | Verified: every dependency below installs on 3.13 and 3.14 |
| Packaging | `uv`, `pyproject.toml`, `uv.lock` | One tool for environment, lock and running |
| Web | FastAPI + uvicorn (ASGI) | The owner's choice among ASGI frameworks. ASGI is needed for the event stream and for agent work that runs for minutes. Routes are added from the operation registry with `app.add_api_route`, and FastAPI serves interactive API documentation at `/docs` |
| Types | Pydantic 2 | Source of truth. JSON Schema is exported from it |
| Database | SQLite through the standard `sqlite3` module, hand-written SQL in repositories | Views, triggers and FTS5 need SQL anyway. No ORM |
| Keyword search | SQLite FTS5 (BM25) | Built in |
| Vectors | Embeddings stored as BLOBs in SQLite. Distance computed by the `sqlite-vec` extension, with a numpy fallback | One database file. No second store to keep consistent |
| Embeddings | `fastembed` (ONNX, Apache 2.0), model `BAAI/bge-small-en-v1.5`, behind an `Embedder` protocol | Local and free |
| Parsing | Docling (MIT) for PDF, DOCX and images. `pypdf` and `python-docx` as the basic parser. Standard library for txt, md, csv | Free, layout-aware, OCR built in |

| MCP | Official Python SDK `mcp` 2.x, class `MCPServer`, protocol revision 2026-07-28 | Current |
| HTTP client (MCP side) | `httpx` | Async, streaming |
| Config | `pydantic-settings`, prefix `TWYF_` | Typed settings |
| Lint and format | `ruff` | |
| Type check | `pyright` in strict mode | |
| Tests | `pytest`, `pytest-asyncio`, `pytest-cov` | |

Everything is free and open source. Nothing needs an account.

## 5. Running it

| Command | What it does |
|---|---|
| `uv run twyf serve` | Applies migrations, loads `.agents`, serves the API on `127.0.0.1:8321`. If `TWYF_STATIC_DIR` is set, also serves that folder at `/`, so the built UI and the API share one port |
| `uv run twyf mcp` | Starts the MCP server on stdio. `--http` serves Streamable HTTP on `127.0.0.1:8322/mcp` |
| `uv run twyf seed-demo` | Creates the demo workspace from `backend/tests/fixtures/demo/` |
| `uv run twyf export-contract` | Writes `contract/schema.json` |
| `uv run twyf events --tail` | Prints the event log (`02-data-model.md` section 5) |
| `uv run twyf eval` | Runs the evaluation set (`07-test-plan.md` section 8) |

All commands are run from `backend/`.

### Hosting later

Version 1 runs locally with one command. Three parts of this design assume one long-lived process: the engine task that runs a question, the in-process event broker behind the stream, and the SQLite file. A container platform that keeps a process alive (for example Cloud Run or Fly) runs it unchanged. A function platform that freezes between requests (for example Lambda) would need the engine moved to a worker and the database moved off local disk. The `queue` runtime and the stored event stream already keep all state in the database, so that move changes `engine.py`, `http/sse.py` and `db/connection.py` and nothing else.

## 6. Configuration and secrets

`config.py` defines `Settings` (pydantic-settings, env prefix `TWYF_`, optional `.env` file in `backend/`).

| Setting | Default | Meaning |
|---|---|---|
| `TWYF_DATA_DIR` | `~/.twyf` | Holds `twyf.db`, `blobs/`, `logs/` |
| `TWYF_AGENTS_DIR` | nearest `.agents` folder above the working directory | Agent definitions |
| `TWYF_HOST`, `TWYF_PORT` | `127.0.0.1`, `8321` | API address |
| `TWYF_STATIC_DIR` | unset | Folder to serve at `/` |
| `TWYF_CORS_ORIGINS` | `http://localhost:5173` | Allowed browser origins |
| `TWYF_RUNTIME` | `queue` | `fake`, `queue` or `command` |
| `TWYF_COMMAND` | `["claude","-p","--output-format","json"]` | Command for the `command` runtime |
| `TWYF_MAX_VERIFY_ROUNDS` | `3` | Decision 17 |
| `TWYF_MAX_DISCUSSION_STEPS` | `6` | Orchestrator review steps per round |
| `TWYF_MAX_TURN_RETRIES` | `2` | Retries of a turn whose output is invalid |
| `TWYF_TURN_TIMEOUT_S` | `300` | Per turn |
| `TWYF_MAX_UPLOAD_MB` | `50` | |
| `TWYF_PARSER` | `auto` | `auto` (Docling if installed, else basic), `basic`, `docling` |
| `TWYF_EMBEDDER` | `fastembed` | `fastembed`, `hash` (tests) or `none` (keyword only) |
| `TWYF_RETRIEVAL_MODE` | `hybrid` | `keyword`, `vector`, `hybrid` |
| `TWYF_FIRST_READ` | `true` | Queue a summary turn after each upload |

The non-secret settings that shape behaviour are snapshotted into `config_versions` (`02-data-model.md` section 4.9), so each question records the settings it ran with.

**Secrets.** The first version holds none: the harness or CLI holds its own model credentials. When an `api` runtime is added, keys come from environment variables only. They are never written to the database, the event log or logs. `Recorder` rejects payload keys named `api_key`, `token`, `authorization` or `password`.

## 7. Concurrency

- One server process. SQLite in WAL mode, `busy_timeout=5000`, `foreign_keys=ON`.
- Service functions are synchronous and each opens its own connection. HTTP handlers call them with `fastapi.concurrency.run_in_threadpool`. The engine calls them with `asyncio.to_thread`.
- Every write is one short `BEGIN IMMEDIATE` transaction that includes its `app_events` row. Model calls never happen inside a transaction.
- Several questions and uploads may run at once. One session runs one question at a time: a second `ask` on a busy session gets error `conflict`.
- Volunteer turns and work turns of one step run concurrently with `asyncio.gather`.

## 8. Failure handling

| Failure | What happens | What the log shows |
|---|---|---|
| Turn output fails validation | Retried up to `TWYF_MAX_TURN_RETRIES` with the validation error added to the input | `turn.failed` then a new `turn.queued` with `attempt` + 1 |
| Turn times out or the runtime errors | Same retry. After the last retry a translator is dropped from the round (`leave` event) and the round continues. An orchestrator, verifier or chat agent failure ends the question | `turn.timed_out`, `question.failed` |
| Partial huddle (some translators failed) | The orchestrator continues with the statements it has | `huddle.member_left` with reason `failed` |
| Verifier cannot be run | The question ends as failed. No answer is returned, because nothing unverified may be presented | `question.failed` with code `verifier_unavailable` |
| Question cancelled | The engine task is cancelled, queued turns are marked cancelled, the stream ends with a `cancelled` event | `question.cancelled` |
| Server crash mid-question | At the next start every question in a non-final state is marked `interrupted` and its queued turns cancelled. The user's message is kept. No automatic resume | `question.interrupted` with source `internal` |
| Parse failure on upload | The file is stored, its extraction has status `failed`, the file is listed with status `unreadable` | `file.extraction_failed` |
| No `queue` worker connected | Turns wait. After 10 seconds the stream carries a `status` event saying no agent runtime is connected | `runtime.waiting` |

The stream of a failed question ends with an `error` event (`03-contract.md` section 4). A failed or cancelled question never produces an `answer` event.

## 9. Security and untrusted content

- **File contents are data.** Passages are passed to agents inside delimiters with a standing instruction (`04-agents.md` section 7). Agents return structured output only, and turns have no tools, so an injected instruction cannot make the backend act. Injected text can at worst produce a wrong statement, which must then pass the quote check and the verifier.
- **Uploads.** Size is limited by `TWYF_MAX_UPLOAD_MB` and enforced while streaming to disk. The original file name is stored as text and is never used as a path. Blobs are stored as `blobs/<first two hex>/<sha256>`.
- **Network.** The server binds to `127.0.0.1` only. There is no sign-in, so it must not be exposed. CORS allows only `TWYF_CORS_ORIGINS`.
- **Source header.** A client names its door in the `X-TWYF-Source` header. With no sign-in this is trusted. It is a record, not a control.
- **Harness risk.** With the `queue` runtime the harness has its own tools. A passage could try to instruct it. The worker prompt forbids following instructions in passages, and `06-mcp.md` section 6 tells the owner to run the worker with file and shell tools disabled.

## 10. Privacy: what leaves the machine

| Part | Leaves the machine |
|---|---|
| Storage, parsing, chunking, keyword search | Nothing |
| Embeddings (`fastembed`) | Nothing at run time. The model file is downloaded once from Hugging Face |
| Docling | Nothing at run time. Its models are downloaded once from Hugging Face |
| Runtime `fake` | Nothing |
| Runtime `queue` | Each turn's prompt, including file passages and notes, goes to the harness that claims it, and from there to that harness's model provider |
| Runtime `command` | The same, to the provider behind the configured CLI |

With a local model behind the harness or CLI, nothing leaves the machine. Whole files are never sent: only retrieved passages.

## 11. Observability, cost and performance

- **Event log.** `app_events` is the main tool. `twyf events` and `GET /api/v1/events` filter it by workspace, question, type and time.
- **Logs.** Standard `logging`, one JSON object per line, to stderr and `logs/twyf.log`. Each line carries `request_id` and, when present, `question_id` and `turn_id`.
- **Cost.** Every turn records input tokens, output tokens, model name and duration on `agent_turns` and in its `turn.completed` event. `question.completed` carries the totals. The `queue` runtime records what the harness reports, which may be nothing.
- **Performance.** Vector search is exact (brute force). This is fast enough up to about 100,000 chunks per workspace. Beyond that, replace `VectorIndex` (`05-retrieval-and-citations.md` section 4).

## 12. Linting, type checking and CI

`.github/workflows/ci.yml`, on push and pull request:

| Job | Steps |
|---|---|
| `backend` | `uv sync --frozen`, `uv run ruff check`, `uv run ruff format --check`, `uv run pyright`, `uv run pytest --cov=twyf --cov-branch --cov-fail-under=90` |
| `frontend` | `npm ci`, `npm run build`, `npm test` |
| `contract` | `uv run twyf export-contract`, `npm run gen:contract`, `git diff --exit-code contract/ frontend/src/backend/contract.gen.ts` |
| `demo` | Start `twyf serve` with the fake runtime and the demo script, seed the demo, run `npm test` with `TWYF_TEST_BACKEND_URL` set |

No job needs a network model, an API key or a model download. Tests use the `hash` embedder and the `basic` parser.
